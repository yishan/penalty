# Penalty v2.0.0 双设备 BLE 联机对战设计

日期：2026-09-24 · 状态：M3 双机主路径已确认；M4 构建／宿主测试通过，真机待验收 · 目标版本：v2.0.0 · 协议：`penalty-ble/1.0`

## 1. 结论与设计边界

用户已确认“连击”是输入错误，目标是“BLE 联机模式”：两台安装同一 Penalty v2.0.0 固件的 AI Passport 在近距离直连，一台玩家射门，另一台玩家守门，每球后交换攻守。

采用“产品对等、单局单主机”的模型：两台设备运行同一固件，用户可任选一台创建或加入比赛；创建方在该局中同时充当 BLE Peripheral、GATT Server 和唯一结果权威，加入方充当 BLE Central、GATT Client。BLE 链路角色不决定谁先射门。双方进入抛硬币页后，仅创建方可按 OK 触发抛硬币；结果仍由固件随机锁定，而不是由创建方选择。

v2.0.0 的联机实现必须与 v1.5.0 单机玩法隔离：

- “点球决胜、点球练习、守门练习”继续使用现有 `penalty_model`，规则、概率、输入时序、界面与音效不得因 BLE 改造而改变。
- 只有进入“联机对战”后才初始化 NimBLE；退出联机后必须完整停止连接、扫描、广播、会话任务和回调。
- `UP` 长按在任意页面仍优先返回 factory Launcher；游戏内 `OK` 长按仍返回 Penalty 封面；封面 `OK` 长按仍被消费；启动不得调用 `launcher_contract_mark_valid()`。
- M1–M3 已实现，M3 真机主路径已由用户确认，M4 将正式联机 UI 扩展为完整比赛和恢复。独立 M2 真机诊断页继续保留：封面长按 DOWN 进入 `BLE LINK TEST`，固定使用大厅码 `4072`；UP 启动创建端／Host，DOWN 启动加入端／Guest；两台显示的六位数一致时分别按 OK，随后 Guest 自动执行加密 ping 与快照检查；长按 OK 会完整停止 BLE 并返回封面。该临时页面不是正式大厅或游戏流程。完整双机验收完成前不修改发布版本号或宣称 v2.0.0 可交付。开发授权不包含提交、推送、发布或刷机。

### 1.1 当前基线证据

- 权威工作树当前位于 `feature/penalty-ble-v2`，HEAD 为已提交的 M1 基线 `3ba1f63f7d74dfb12299f0b7846f163043617890`；本方案不读取或修改 `release/penalty-1.x` 的工作内容。
- `penalty_model` 当前以单机玩家为中心；`aim()` 会在每球开始时锁定 AI 方向、绿区和结果随机值，`settle()`／`settle_match()` 负责一次结算，`penalty_model_resync()` 只重置未提交输入而不重抽隐藏决定。这些是双机 exactly-once 和重连设计的继承基础。
- v1.5.0 基线的 `sdkconfig.defaults` 只启用 NimBLE Peripheral/Broadcaster，Central/Observer 关闭。M2 现已同时启用两组角色、GATT Client 和 Secure Connections，仍限制单连接且不持久化 bond。无关的 `demo_ble.c` 继续不进入 Penalty 构建。
- v1.5.0 的 ESP-IDF 5.5.3 构建记录为 PASS，应用大小 1,496,832 字节，但 v1.5.0 双机、堆／栈和真机测试均未运行。约 249,200 字节空闲堆和 114,688 字节最大连续块来自较早的 v1.4.1 启动记录，不能冒充 v1.5.0 当前测量。
- `main/main.c` 现有 shell 已在页面输入前拦截 `UP LONG`，调用 `launcher_contract_return_to_factory()` 并记录所有错误；这个顺序是 v2.0.0 的硬契约。

## 2. 目标、非目标与默认玩法

### 2.1 目标

1. 两台设备在无手机、无 Wi-Fi、无云端的前提下完成发现、确认、加密连接、一局绑定、五轮点球与断线恢复。
2. 双方输入在本机按键源时间锁定，网络延迟不改变已经锁定的方向或时机值。
3. 主机只结算一次，并向双方广播同一个结果、比分和完整可恢复状态。
4. 重复、乱序、丢包或短时断线不能重复计分、重抽结果、跳过回合或让两台设备永久分叉。
5. 保持固定内存；不保存无限历史，不逐包分配内存，不把动画帧或球坐标通过 BLE 传输。

### 2.2 非目标

- 不做互联网匹配、账号、排行榜、观战、三人以上比赛或跨版本回放。
- 不做恶意固件检测、硬件证明或竞技级反作弊；安全边界是假定双方运行官方同版本固件，但链路必须防止普通旁观设备误连、窃听和注入。
- 不在 v2.0.0 恢复掉电前的比赛；任一设备重启后本局结束。
- 不让 BLE 控制 Launcher、OTA、NVS 擦除、文件写入或其他非 Penalty 能力。
- 不启用 Wi-Fi/BLE 共存；联机对战期间 Wi-Fi 保持未初始化。

### 2.3 默认比赛流程

1. 标题页保留现有五行；选择“点球决胜”后进入二级菜单，再选择“单机对 AI”“创建联机”或“加入联机”。
2. 创建方显示四位大厅码并开始有时限的可连接广播；加入方只显示协议兼容的 Penalty 大厅码。
3. 加入方选择相同大厅码，建立 BLE 连接；双方显示同一六位安全比较码，并分别确认。
4. 双方进入同一抛硬币页；创建方按 OK 后，Host 随机锁定并公布结果和先后手，加入方只等待结果，不能触发或选择硬币面。
5. 每球双方同时、盲选：射手选择目标与力量，门将选择扑救目标与时机；任一方在另一方揭示前都不能看到对手选择，不再提供由射门方向派生的门将动作提示。
6. 双方先提交选择摘要，待两边都提交后再揭示原始选择；Host 验证摘要并用双方输入和该球预先锁定的随机材料结算。双方本地播放动画，不传输动画帧。
7. 每球后交换射手和门将。双方各最多五球，按 v1.5.0 的提前结束和成对突然死亡规则判定。

### 2.4 推荐的二级菜单

为保留 v1.5.0 标题页的五行密度和三个既有玩法，推荐让现有“点球决胜”成为对战入口：

```text
点球决胜

> 单机对 AI
  创建联机
  加入联机
  返回

UP/DOWN 选择 · OK 确认
```

“单机对 AI”进入当前 v1.5.0 点球决胜，不改变玩法，只比现在多一次确认。“创建联机”显示四位大厅码并等待加入；“加入联机”扫描兼容大厅并用 UP／DOWN 选择四位码。这样主标题不用增加第六行，设置和说明位置也不变。代价是进入单机点球决胜多一步，该二级菜单方案已确认接受。

## 3. 角色、身份与一局绑定

### 3.1 四类角色必须分开

| 维度 | 创建方 | 加入方 | 说明 |
| --- | --- | --- | --- |
| 产品身份 | 对等设备 A | 对等设备 B | 固件和功能相同 |
| BLE GAP | Peripheral | Central | 仅负责广播、扫描和建链 |
| GATT | Server | Client | 仅负责属性与消息传输 |
| 比赛权威 | Host | Guest | Host 决定状态、随机材料、结算和快照 |
| 当前回合 | Shooter 或 Keeper | Keeper 或 Shooter | 每球交换，与 BLE 角色无关 |

不使用“主机永远先射”或“Central 永远权威”等隐含规则。创建方只拥有“按 OK 触发随机抛硬币”的操作权，不拥有选择硬币结果或先后手的权力。断线重连后上述 Host/Guest 身份不交换。

### 3.2 设备与比赛身份

- `boot_instance_id`：每次启动生成的 64 位随机实例号，只用于区分本次运行，不写 NVS。
- `match_id`：创建比赛时生成的 128 位随机值，完整值只在加密握手与快照中传输；界面只显示四位大厅码。
- `match_epoch`：本局内每次恢复或重新建链递增，用于拒绝旧连接残留消息。
- `peer_instance_id`：绑定时记录对端本次启动实例。断线恢复只接受同一对端；其他设备不能接管进行中的比赛。
- `session_tag`：握手后从 `match_id` 和双方随机数派生的短标识，放在常规消息中，避免每包携带完整 `match_id`。

BLE 地址不能作为永久玩家身份；随机地址、隐私地址和设备重启都会使它不适合作为业务主键。v2.0.0 不建立账号或永久设备昵称。

### 3.3 绑定生命周期

绑定从双方完成安全比较并接受比赛设置开始，到比赛结束、用户取消、重连超时或任一设备重启时结束。默认只保留 RAM 中的会话和临时 bond，不把比赛、比分、恢复令牌或对端身份写入 NVS。

“重新配对”是破坏性会话操作：先明确取消旧比赛、递增 epoch、删除该局临时密钥和消息缓存，再重新进入创建／加入流程。不能在旧比赛仍可恢复时静默绑定第三台设备。

## 4. 发现、连接与安全确认

### 4.1 广播与扫描

- 为 `penalty-ble/1.x` 分配独立 128 位 Service UUID；协议主版本不兼容时使用不同 UUID 或在连接前明确过滤。
- Legacy Advertising 主包只放 Flags、Service UUID 和必要字段；大厅码、协议次版本与能力位放入 Scan Response，不能假设超过 31 字节的广播空间。
- 创建方前 10 秒采用约 100 ms 快速广播，随后放慢到约 500 ms；60 秒无人加入则停止并询问重试。
- 加入方主动扫描，只列出同一 Service UUID、可解析且信号仍新鲜的大厅。列表按最近收到时间和 RSSI 展示，但 RSSI 只用于排序，不作为身份或距离证明。
- 一旦进入安全握手，创建方停止接受第二条连接；`CONFIG_BT_NIMBLE_MAX_CONNECTIONS` 保持 1。

### 4.2 两层确认

四位大厅码只用于防止用户选错附近设备，不属于密码学认证。连接后必须启用 LE Secure Connections、MITM 保护和链路加密；两台都有屏幕和三键，优先使用 Numeric Comparison：双方显示相同六位数，UP／DOWN 选择“匹配／不匹配”，OK 确认。

六位安全比较码不是第二个房间密码，也不需要用户输入。它由 BLE 配对过程临时生成，用来确认“我眼前这两台设备建立的是同一条加密连接”。如果附近有人在中间冒充，两边显示的数字通常不会一致，用户选择“不匹配”即可断开。四位大厅码解决“选哪一台”，六位安全码解决“连接过程中有没有被第三方替换”。

只有 `encrypted=1` 且 `authenticated=1` 后才允许写入比赛 Control Point。安全失败、用户拒绝、超时或协议不兼容时立即断开，不创建 `match_id` 绑定。固定 passkey 和 Just Works 仅可用于开发诊断，不作为 v2.0.0 交付默认值。

默认不跨重启保存 bond。短时断线可复用本次启动内的密钥；若实现中确认 ESP-IDF 5.5.3 的所选 NimBLE 存储路径必须持久化 bond，需把 NVS key 命名空间、删除时机和完整镜像重置影响单独评审，不能借用语言偏好键。

## 5. 状态机与回合权威

### 5.1 会话状态

联机会话层使用独立纯 C 状态机，至少包含：

```text
OFF
  -> CREATE_ADVERTISING | JOIN_SCANNING
  -> CONNECTING
  -> SECURING
  -> BINDING
  -> LOBBY_READY
  -> COIN_READY
  -> COIN_TOSS
  -> ROUND_OPEN
  -> WAIT_ACTION_COMMITS
  -> WAIT_ACTION_REVEALS
  -> RESOLVING
  -> RESULT_COMMITTED
  -> HANDOFF | MATCH_SUMMARY
  -> PAUSED_RECONNECT
  -> MATCH_ABORTED | OFF
```

UI 只呈现会话状态；NimBLE 回调只复制有界事件到队列；会话任务解析协议并产生纯 C 事件；任何非 LVGL 任务访问界面都必须通过现有应用更新路径并持有 `bsp_lvgl_lock()`。

### 5.2 每球时序

1. Host 创建 `round_id`，锁定两份结果随机数及其承诺摘要，发送带相对开始延迟的 `ROUND_OPEN`。双方从同一逻辑起点进入操作，但各自使用本机单调时间。
2. Shooter 在本机沿用六格选择和力量条，形成 `SHOT_ACTION(round_id, target, power, action_nonce)`；Keeper 同时沿用六格选择和时机条，形成 `SAVE_ACTION(round_id, target, timing, action_nonce)`。双方 UI 都不显示对方进度、目标或完成时间。
3. 每台设备先发送 `ACTION_COMMIT = SHA-256(match_id, round_id, role, action fields, action_nonce)`，只暴露摘要，不暴露选择。Host 自己也必须先固定本机 commit，不能等 Guest reveal 后再修改。
4. Host 收齐两个 commit 后发送 `REVEAL_REQUEST`；双方再发送原始 action 和 nonce。任何 reveal 与既有 commit 不匹配都使该球进入协议错误／快照恢复，不得结算。
5. Host 验证双方动作属于当前 round/phase、字段合法且尚未结算，然后调用纯 C 对战规则一次，生成 `result_id` 和完整 `ROUND_RESULT`。
6. `ROUND_RESULT` 持久留在本局 RAM 快照中。两边确认收到后，Host 发 `ANIMATION_START(delay_ms)`；两台用本地计时播放现有动画和音效，允许小量视觉偏差，不同步每一帧。
7. 只有 `result_id` 首次应用时才更新比分。动画结束只改变展示状态，不能再次结算。

### 5.3 双人结算规则

v1.5.0 的射门概率表和守门概率表原本分别面向 AI 对手，不能未经确认直接叠加为 PvP 规则。推荐的 v2.0.0 组合方式是分两步使用独立随机数：

1. 射门质量先决定是否射正：深绿线 95%，普通绿区 80%，合法但绿区外 35%；弱射、过高或超时直接未射正。
2. 仅在射正时计算扑救：同格时深绿线／普通绿区／绿区外为 90%／65%／25%；同列另一格为 35%／20%／5%；不同列为 0%。

最终结果是“射正且未被扑出”才进球。两个 0–99 随机值在 `ROUND_OPEN` 前锁定，结果消息中揭示，双方可重算核对。这个组合沿用两套已验证表，但会使“完美射门遇上完美同格扑救”的进球率约为 9.5%；该规则已确认用于实施，仍需真机试玩，后续可单独调整平衡性。

取消方向提示后，联机难度不再控制 900／600／350 ms 的提示可见时间；建议只统一控制双方时机条的绿区宽度和速度，且同一局两边参数完全相同。若保留其他难度差异，必须在大厅中明示，不能让 Host 和 Guest 获得不同窗口。

### 5.4 信任与反作弊边界

提交动作一经本机模型锁定就不可修改，远端动作在双方 commit 完成前不能进入任何一方的 UI 决策路径。由于创建方同时是 Host，commit/reveal 在本方案中从“可选审计”提升为首版协议要求，用来保证纯猜测流程下 Host 也不能先看 Guest 原始选择再操作。它仍不抵抗被修改的恶意 Host 固件：恶意固件可伪造本机输入、随机数或最终结果。v2.0.0 的目标是保证官方固件公平顺序、防偶发分叉、重放和普通附近攻击，不是电竞级可信裁判。

## 6. GATT 与应用协议

### 6.1 GATT 服务

| Characteristic | 方向 | 属性 | 用途 |
| --- | --- | --- | --- |
| Protocol Info | Server -> Client | Read | 协议、固件、能力、最小兼容版本 |
| Control Point | Client -> Server | Write with Response | Guest 动作、确认、快照请求、退出 |
| Event Stream | Server -> Client | Indicate | Host 权威事件、结果、错误、快照分片 |
| Session Status | Server -> Client | Read + Notify | 轻量状态、当前 seq/epoch、恢复入口 |

关键状态不使用 Write Without Response。GATT write response 或 indication confirmation 只证明链路传输完成，不证明业务状态已经应用，因此协议仍保留 `seq`、`ack_seq`、`action_id` 和 `result_id`。

### 6.2 版本与能力协商

- 固件版本：`2.0.0`，用于产品发布和诊断。
- 协议版本：`penalty-ble/1.0`，独立于固件 SemVer。
- 快照 schema：`1`。
- 主版本不同：立即拒绝，并显示“版本不兼容”。
- 主版本相同、次版本不同：取双方都声明支持的最低能力集；任何 required capability 缺失则拒绝。
- 首版能力位至少包括 `DUEL_V1`、`COMMIT_REVEAL_V1`、`SNAPSHOT_V1`、`RECONNECT_V1`、`SC_NUMERIC_COMPARE`。

### 6.3 消息信封与大小

所有字段使用明确字节序、定长整数和边界检查。逻辑消息信封至少包含：

```text
protocol major/minor
message type + flags
session_tag + match_epoch
sender_seq + ack_seq
round_id + phase
payload_length
payload
```

握手和快照包含完整 `match_id`，普通回合消息只用 `session_tag`。实现可请求 64–128 字节 ATT MTU，但必须在默认 MTU 23 下正确工作；超过单个 characteristic value 的消息使用有界分片，分片包含 snapshot/result ID、索引、总数和总长度。单个逻辑消息上限为 256 字节，接收缓冲和分片数均为编译期上限。

### 6.4 可靠性规则

- 每个方向使用独立 32 位单调 `seq`；每个用户动作另有在一局内唯一的 `action_id`。
- `seq` 小于等于已应用值：视为重复，重发之前缓存的 ACK／结果，不再执行业务动作。
- `seq` 大于期望值：不猜测中间状态，不应用；回复 `STATE_REQUIRED` 并请求完整快照。
- round、phase、role 或 epoch 不匹配：拒绝动作并发送当前权威状态。
- 已连接时 300 ms 未获业务 ACK 可重发，最多 3 次；随后请求快照。连续失败转入 `PAUSED_RECONNECT`，不得把超时判为进球。
- 发送队列满时可丢弃可重建的状态通知，但不能覆盖未确认的动作、结果或退出；发生关键队列溢出时进入暂停并请求快照。
- 所有解析失败只记录脱敏的类型、长度、seq 和错误码，不记录安全比较码、完整 `match_id` 或密钥材料。

### 6.5 权威快照

快照包含协议/schema、完整 match/epoch、Host/Guest 实例、比赛阶段、难度、先后手、round、双方射门次数与比分、当前角色、双方 commit/reveal 是否完成、最近已提交 result、双方最后 seq/ack 和比赛结果。两边 reveal 完成前，快照不得包含任一方隐藏目标、力量、时机或 nonce。

Guest 应用快照时以 Host 为准，不合并本地比分。若本地存在已发送但未被 Host 确认的同一 `action_id`，恢复后可原样重发；Host 已确认的动作不得生成新随机数或新 ID。

## 7. 延迟、时钟与动画同步

- 按键判定只使用事件源捕获的本机单调时间；不把收包时间当成力量或扑救时机，避免网络延迟改变结果。
- Host 的阶段和超时使用 Host 单调时间；双方时钟不要求同 epoch，也不在协议中传输绝对墙钟。
- 活跃回合建议请求 30–45 ms connection interval、latency 0；大厅或交接等待可请求 60–90 ms、peripheral latency 3。实际参数由 Central 和控制器协商，失败时必须继续工作并记录结果。
- 目标：同室稳定连接下，本机锁定输入到 Host ACK 的 P95 不超过 150 ms；双方最后一个动作锁定到两台开始结果动画的 P95 不超过 300 ms；视觉／音频起播偏差目标不超过 100 ms。以上是待真机测量的验收目标，不是当前事实。
- `ANIMATION_START` 使用相对延迟（建议 150–200 ms），不是跨设备绝对时间。对战不传画面、坐标或逐帧时钟。

## 8. 丢包、断线与重新配对

### 8.1 断线时的确定性处理

| 断线点 | 恢复行为 |
| --- | --- |
| 双方 commit 前 | 重连后回到同一 `ROUND_OPEN`，清除本轮未提交选择，不消耗射门 |
| 只有一方 commit | 保留该 commit 但不揭示；重连后另一方可重新选择并 commit |
| 双方已 commit、尚未全部 reveal | 保留 commit；重连后继续 reveal，任何一方不得修改动作 |
| 双方已 reveal、结果未提交 | Host 用同一动作和随机材料完成一次结算 |
| 结果已提交、动画未完成 | 快照携带同一 `result_id`；补显示稳定结果，不重复计分 |
| 交接或总结页 | 恢复同一比分和页面，不自动开始下一球 |

断线立即冻结新输入，页面显示“连接中断／正在重连”；不得将对端掉线判为失球或进球。

### 8.2 重连策略

- GAP 断线后进入 30 秒恢复窗口。原 Peripheral 只广播带恢复标记的同一 session，原 Central 只连接同一 peer/session。
- 前 10 秒快速重连，之后降低扫描／广播占空比。每 2 秒更新一次 UI 倒计时，不用高频日志刷屏。
- 重新建立加密链路后交换 `RESUME(match_id, epoch, last_applied_seq, state_digest)`，Host 递增 epoch 并发送快照。
- 30 秒超时按已确认规则判为“比赛中止，无胜负”，清除临时绑定并返回联机入口，不判掉线方负。
- 任一设备重启后不恢复本局；对端收到新 `boot_instance_id` 时中止旧局。

首版推荐“无胜负中止”：BLE 掉线可能来自距离、电量、射频干扰或重启，设备无法可靠区分恶意逃跑和真实故障；v2.0.0 又没有账号、排名或赛季积分，判负的收益有限，误判成本更高。以后若增加竞技记录，可把“主动退出立即判负、链路故障给恢复窗口、超时判负”作为独立规则升级。

### 8.3 主动退出

`OK` 长按优先执行本地取消：尽力发送一次 `MATCH_END(USER_CANCELLED)`，但不等待网络完成才返回封面。对端收到后进入“对方已退出”，确认后返回联机入口。`UP` 长按继续由 shell 在任何页面输入之前处理，直接执行 Launcher 返回协议；联机会话不得拦截、改键或增加额外 Launcher 提示文字。

## 10. 内存、Flash 与功耗预算

### 10.1 已知基线与目标预算

ESP32-C3 无 PSRAM，显示、24 KB LVGL 池、音频、NimBLE、任务栈和 DMA 竞争内部 RAM。v1.4.1 真机启动曾记录约 249,200 字节空闲堆、114,688 字节最大连续块；v1.5.0 尚无对应真机堆／栈测量，因此这些数字只用于制定测试，不作为 v2.0.0 当前余量证明。

建议接受门槛：

- 应用协议层所有固定队列、快照、重传缓存和分片缓冲合计目标不超过 8 KB；热路径零逐包 heap allocation。
- NimBLE 保持单连接、单 bond、最少 CCCD／GATT procedures；安全功能不能为了省约 2 KB RAM 而关闭。
- 双机已连接且联机 UI／音频空闲时，目标空闲堆不少于 160 KB，最大连续块不少于 64 KB；以相同页面的 v1.5.0 实测为对照，记录 BLE 增量。
- 每个新增任务记录 stack high-water；验收目标至少保留 768 字节余量。50 次进入／退出、50 次重连和连续 20 局后不得出现进行性堆下降、任务泄漏、看门狗或重启。
- 固件仍须适配当前 8 MB 分区与 Launcher app-slot 契约；本功能不要求新增分区或擦除 NVS。

以上阈值属于工程预算，必须在真实 v2.0.0 构建和真机上验证并根据证据调整。

### 10.2 功耗策略

- 联机入口之外不启用 BLE。创建大厅超时后停止广播；加入页面退出后停止扫描。
- 活跃输入阶段用低延迟参数，交接／总结阶段请求较低占空比；不依赖参数更新一定成功。
- 沿用现有 60 秒无操作背光降亮逻辑，但联机状态提示和用户操作会刷新活动时间。
- v2.0.0 首版不默认启用自动 Light-sleep：现有 50 ms LVGL timer、音频和 BLE 时序需要先做实测。后续只有在 `CONFIG_PM_ENABLE`、tickless idle、外设锁和输入唤醒均验证后再单独评审。
- 不承诺续航时长。双机验收记录 30 分钟大厅等待、60 分钟持续比赛的电量／电流、温升和断链情况；无电流仪表时明确标为未验证。

## 11. 主机测试与故障注入

### 11.1 纯 C 对战模型

- 两种先手、创建方触发但不能选择抛硬币结果、双方固定交替、五轮提前结束边界、平局进入成对突然死亡、第一球不能结束加赛。

## 12. 双机真机验收矩阵

两台设备必须刷入同一候选构建；刷机另行取得明确授权。至少覆盖：

1. A 创建/B 加入和 B 创建/A 加入各一次；多大厅、选错码、取消、安全码匹配／拒绝、60 秒超时、协议不兼容。
2. 创建方按 OK 触发两种随机先手、三档难度、双方同时盲选、双方各六个目标、弱射／过高／超时、同格／同列／异列扑救、常规提前结束和至少一场突然死亡。
3. ROUND_OPEN、单边 commit、双边 commit、单边 reveal、双边 reveal、结果已提交、动画中、交接页和总结页分别强制断链；确认 30 秒内恢复且不泄露选择、不允许改选、不重抽、不重复计分。
4. 超过恢复窗口、对端重启、第三台设备尝试接管和主动重新配对；旧会话消息不得进入新局。
5. 记录输入到 ACK、最后动作到结果动画、两机动画起播偏差、RSSI、断链原因；近距离、3–5 米视距和人体遮挡分别测试，但不预先承诺无线距离。
6. 50 次联机进入／退出、50 次重连、20 场完整比赛和至少 60 分钟连续运行；记录 free/min heap、largest block、各任务 stack high-water、队列峰值、看门狗和复位原因。
7. 联机期间音效、显示、按键、电量轮询无明显卡顿；退出后单机三个模式逐一完整游玩，行为与 v1.5.0 一致。
8. 在发现、配对、比赛、重连和总结页逐一验证 `UP` 长按返回 Launcher；验证游戏内 `OK` 长按只回 Penalty 封面，启动不 mark valid。
9. 使用普通 BLE 扫描器确认未认证设备不能写比赛特征；发送畸形、超长、旧 epoch 和错误 role 消息，设备应拒绝并保持可恢复，不崩溃、不泄露密钥。

### 14.1 M3 实现检查点

M3 已实现“点球决胜”二级菜单（单机／创建联机／加入联机／返回）、最多四个兼容的附近大厅、四位大厅码、显示六位安全码后确认、Host 选难度与 Guest 确认，以及创建方触发随机先手。两名玩家独立选择六个目标并操作时机条；双方都看不到对手方向提示。双方提交 commitment 后，Host 请求 reveal 并发送结果；Guest 先验证双方动作 commitment、随机数 commitment 和重新计算的结算，再应用比分。两端展示已结算球路并播放本地音效。双方确认第一球结果后交换射手。测试会话在**两球、每人射门一次**后结束，不宣布整场胜负。

`penalty_multiplayer_core` 是纯 C 协调器；`penalty_multiplayer` 管理 worker、输入队列、BLE 接入和渲染视图。BLE 使用有界逻辑消息队列、ACK／分片处理与五秒出站截止时间。实验能力位 `M3_LOOP_V1` 阻止 M3 大厅与旧诊断固件匹配。生产 nonce 使用 ESP 硬件随机源；确定性随机源仅用于宿主测试。音频和网络不在 LVGL 回调中执行。停止联机时，先暂停 timer，再等待 worker／BLE／音频退出，最后销毁 UI。单机入口不初始化 NimBLE。

历史 M3 候选在断链后无胜负中止，并提供重新连接；**不恢复中断的回合**。M4 在该候选上继续扩展，见下文。时钟同步动画、资源／耐久验收和完整真机故障注入矩阵仍属于 M5–M6。约 180 ms 的相对动画延迟不等于已测得的双机同步。

M3 真机检查必须让两台设备使用同一获准候选固件。一台进入“点球决胜 → 创建联机”，另一台进入“点球决胜 → 加入联机”，选择相同大厅码。核对两端六位数字，按 OK 同意或下键拒绝。Host 用上下键选择难度并按 OK 确认，Guest 按 OK 同意。Host 按 OK 抛硬币。每名玩家用上下键选格子，按 OK 启动时机条，再按 OK 锁定；四秒超时提交零时机。第一球结算后双方按 OK 交换角色；第二球结束后长按 OK 返回封面。交换两台设备的创建角色后再测一次。实体屏幕、音效、真实比分收敛、两种随机先手、配对拒绝、完整退出与运行时资源仍需真机检查。

用户于 2026-10-04 确认 M3 双机大厅／安全／对局／角色交换主路径均正常。这是用户观察的主路径验收，不是仪器测得的 heap／stack、拒绝路径、耐久或恢复验收。

### 14.2 M4 实现检查点

当前协调器运行双方各五球、提前结束和成对突然死亡，直到产生胜者。非末球结算后，双方确认才进入下一球。结束页显示本机胜负、相同比分和常规／加赛阶段；OK 开始新大厅。单机难度、输入时序、概率和音频行为不变。

M4 要求实验能力位 `M4_MATCH_V1` 以及 duel、commit/reveal、reconnect 能力，不能匹配 M2 诊断或 M3 两球大厅。加密 Protocol Info 在原有 20 字节后追加两字节 Host 连接 epoch。每次认证物理重连递增 epoch，seq 在新 epoch 内重新开始，旧 epoch 帧直接丢弃，延迟的 GATT procedure 回调受连接 generation 检查。比赛 ID、对方 BLE 身份和启动实例保持绑定。重启后的设备或第三台设备不能接管本局。

每个方向只保留一条不可修改的待确认逻辑消息。只有协调器接受消息后才发应用 ACK。纯 ACK 帧使用 seq 零，不再要求 ACK。重试间隔为 300 ms，最多重试三次。重试保留 epoch／seq／payload，使用新分片 ID；分片发送完成不等于应用已接受。耗尽重试或传输序号缺口会终止物理连接并开始恢复；物理 GATT 操作仍有五秒截止时间。BLE 诊断保留独立 M2 编码和路径。

断线后冻结输入与结算，恢复窗口最长 30 秒；反复断线不延长协调器最初的截止时间。未锁定的选择／蓄力重置到瞄准；已锁定的动作、nonce、commitment 和 Host 随机材料不变。原设备使用仅存在于 RAM 的本局认证 bond 自动重连，不把比赛 checkpoint 或 bond 写入 NVS。退出时停止会话，只删除本局对方的临时记录，不擦除 NVS 或无关记录。

恢复顺序为 Host SNAPSHOT → Guest STATE_ACK → Host RESUME。Guest 验证范围、比赛／回合身份、计数、commitment 和任何遗漏的结算，再确认状态。两端建立恢复状态前不接受新输入。中断的动画恢复到已提交结果，不重复计分或音效。恢复超时或主动取消后无胜负中止，不判掉线方负。暂停页下键取消；OK LONG／UP LONG 保留封面／Launcher 优先级。退出 worker 在有界时间内尝试发送取消通知，再清理资源。双方已确认的全场结束页不会因之后断链而丢失。不支持重启恢复。

恢复 SNAPSHOT 是固定 193 字节的小端 payload，在 `M4_MATCH_V1` 下使用 schema 1：

| 偏移 | 内容 |
| --- | --- |
| 0–19 | 完整比赛 ID 与回合 ID |
| 20–27 | schema、规范化恢复阶段、难度、首位／当前射手、flags、duel 阶段、比赛结果 |
| 28–51 | 结算次数、尝试数、进球数、加赛轮次 |
| 52–59 | 双方时机区间及 commitment／reveal mask |
| 60–155 | 双方动作 commitment 与 Host 随机 commitment |
| 156–172 | 已结算随机 reveal、结果／flags、result ID |
| 173–192 | 双方动作，仅在结算后发送；未结算时全零 |

宿主测试覆盖 180 场完整比赛、双先手、三档难度、提前结束和突然死亡。真实编码／分片故障模拟在 27,211 次传输中交付 16,869 条逻辑消息，注入 10,342 次消息／ACK 丢失和 27,223 次重复到达，拒绝 22,046 次旧 epoch 到达。还覆盖第一球／下一球开启包丢失、锁定／未锁定选择、遗漏结果、反复断线、30 秒超时、取消／重新配对和非法快照。Address／Undefined Behavior sanitizer 通过。实际 LVGL 测试验证双语、所需字形、结束／恢复／无胜负页、盲选门将和原有 24 KiB 池内 50 次创建销毁；单机 preview 回归也通过。这些测试不运行实体 NimBLE 无线、bond 重加密或设备显示。

授权在两台安装 M4 后，先重复正常大厅／安全流程，再完成全场比赛和成对突然死亡。分别在瞄准、单方锁定、双方锁定和结果附近短暂中断无线链路，比较比分，并确认已锁定动作不能修改。两台保持通电：关闭一台测的是重启拒绝，不是恢复。再测试超过 30 秒的中断、暂停页取消、封面／Launcher 返回、新局重新配对，以及拒绝不同设备。运行时 heap／stack、实体显示／音效、动画偏差、50 次重连和 20 局耐久仍需真机验证。

### 14.3 受控断链开发测试版

2026-10-05，用户在约 5 米、隔两堵墙的条件下无法触发 BLE 断线。这是未触发的恢复测试，不代表恢复通过或测得无线范围。用户同意制作仅开发测试使用的受控断链版本；此授权不包含刷机或发布。

`CONFIG_PENALTY_DEV_BLE_FAULTS` 默认关闭。使用 `./tools/validate.sh --all --dev-ble-faults` 构建启用版；配置叠加及独立交付目录见[构建指南](../../../docs/development/engineering/build-and-test.zh_CN.md)。普通版和开发版都保留现有 M4 协议、仅 RAM 的 bond、原设备／启动实例绑定及原有 30 秒恢复截止时间。

两台保持通电并进入已认证对局后，在瞄准、等待对方动作或非末球结果阶段长按下键打开面板。面板显示 `DEV BLE TEST`：单击 OK 断链 10 秒，单击下键断链 35 秒，按上键关闭而不断链。此开发版在这些空闲阶段将下键短按延迟到 CLICK 时处理，因此打开面板不会改变目标。蓄力、抛硬币、配对、恢复、失败和已结束阶段不能打开。关闭或离开适用阶段后清除待处理面板点击。长按 OK 仍返回封面，长按上键仍遵循现有 Launcher 协议；这两种退出不会主动触发测试断链。

联机 worker 只把请求加入队列；BLE worker 重新核对 M4、已绑定认证对方、活动连接、当前连接 generation 及比赛尚未结束，再终止真实 GAP 连接，不伪造游戏断线事件。仅真实断线回调启动 10／35 秒发现暂停。发起设备暂停重新发现，并阻止排队的广播／连接尝试；另一台走正常恢复流程。不修改比赛 ID、commitment、nonce 或随机材料。10 秒暂停结束后走原有认证发现及 SNAPSHOT／STATE_ACK／RESUME。35 秒测试由现有 30 秒截止时间先无胜负中止，不会恢复发现。重复断线回调不能延长暂停。失败、比赛结束、停止和新会话均清除暂停；页面销毁后不存在延迟定时器。测试入口不擦除或持久化设置和 bond 数据。

宿主验证覆盖合法时长、实际断线计时、重复回调、生命周期清理、两种发起角色、10 秒后已锁定动作／随机材料／比赛身份保留，以及 35 秒后两端无胜负超时。现有 180 场故障模拟及 ASan／UBSan 通过。实际 LVGL 面板字形／布局及 24 KiB 池内双语 50 次创建销毁通过；开发标签使用当前所选字体已覆盖的 ASCII。这些是宿主检查，不是真机 GAP／bond 或无线丢失验收。

分别获得仅写 app 的刷机授权后，先在单方已锁定动作时测 10 秒：两台保持供电并近距离放置，在一台打开面板、单击 OK，检查可见恢复阶段、无需重新抛硬币的自动返回、已锁定动作不变及比分一致／不重复计分。换另一台发起再测。在新比赛中单击下键测 35 秒，检查两端约 30 秒后显示无胜负中止，不判负也不恢复比赛。然后新建大厅，检查干净重新配对和正常完整比赛。自然无线丢失／监督超时、各结算边界恢复、实体界面／音效／输入、运行时资源及耐久仍分别待验收。

### 14.4 M5 兼容与资源可观测性

M5 保留单机三个模式、竖屏按键、仅语言持久化及现有 Launcher 契约。不需要修改 BSP、分区、依赖锁、网络协议或比赛规则。进入单机不会启动 NimBLE。预览脚本执行单机和联机两个程序；固件／完整门禁在归档前要求实际 LVGL 渲染检查与 size 报告通过。联机覆盖双语、实际所选字体字形、大厅／安全／难度／硬币、锁定等待、恢复、赢／输／无胜负总结、门将盲选、圆角、局部／整屏刷新一致性，以及未扩大的 24 KiB 池内 50 次页面生命周期。桌面帧缓冲仅用于测试。

BLE 和联机 worker 每秒采样空闲堆／最大空闲块，不在按键／GAP 回调中执行。BLE 退出记录启动前／就绪／停止后的堆、采样最低值、BLE worker／host 栈余量及观察到的内部／公开／发送队列峰值。联机退出记录进入／退出堆、采样最低值、启动以来最低堆、worker 栈、观察到的输入队列峰值／丢弃数／最大事件年龄，以及页面销毁后的 LVGL 空闲／最大块。ESP-IDF 栈值的单位是字节，不是 words。采样最低值／队列峰值可能遗漏瞬时极值；启动以来最低堆不随大厅重置，立即退出时的堆可能尚未完成 idle task 回收。M6 应比较预热后的稳定测量，不以单次瞬时值判断。日志不包含比赛秘密或密钥材料。在真机余量证据出现前，不缩减现有队列容量、6 KiB BLE／联机 worker 栈、24 KiB LVGL 池和局部绘制缓冲。编译期和宿主测试约束固定模型／核心／消息状态，不等于真机堆测量。实体资源／延迟／安全／耐久验收仍属于 M6。
